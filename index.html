I tried to fix a prompt-injection detector by editing its weights by hand, without training or fine-tuning

November 2026 · code and results on GitHub · built with Claude Code, run on Modal

In this article I am gonna share how I tried to improve an open source prompt injection detection model by changing its weights directly by hand. I did not train the model and I did not fine-tune it. I will share what worked, what did not work, and the mistakes I made on the way.

I am sharing this article for educational purposes only and these are my personal opinions.

What is the problem?

A prompt injection detection model checks if a user message is an attack on an AI application. It gives one of two answers: SAFE or INJECTION.

Most of these models have one common problem. If a normal message has words like "ignore" or "bypass", the model thinks it is an attack. For example, "please ignore the typo above" gets marked as an attack. I call this a false alarm.

So I wanted two things from this work:

  • Fewer false alarms on normal messages
  • More real attacks caught

Where the idea came from

I got this idea from a blog post called Weight-Space Programming by Rikiya Takehi.

Normally we improve a model by training it on more data. This blog says something different. A model is just a big list of numbers, and these numbers are called weights. We can look inside the model, understand what is going wrong, and change the numbers ourselves.

I wanted to check if this works on a real security model.

The model I used

I used protectai/deberta-v3-base-prompt-injection-v2 from Hugging Face. It has 184 million weights.

I followed one rule in this work. I can run the model on examples to understand it, but every number I change must come from simple math like averages. No training steps at all.

Finding the problem inside the model

The model reads a message in 12 steps. These steps are called layers. The final answer is made from the output of step 12.

After each step I checked one simple thing. Can the model tell the difference between a real attack and a normal message with scary words? I gave a score out of 100, where 100 means it can always tell and 50 means it is just guessing.

This was the most interesting finding for me. The model already knows the difference in the middle steps. But it loses that knowledge at the last step, just before giving the answer.

Then I checked more closely and found the exact place. It is the last part of the last layer. If I read the model just before this part, false alarms on scary word messages come down to around 15%. If I read just after it, they are around 30%.

So the model is throwing away useful information at the very end.

How I changed the weights

The final answer depends only on one position in the last layer. So I can change the last layer and nothing else in the model gets disturbed. I did four things:

  1. I picked one slot in the last layer and emptied it, so I can use it to carry a new signal.
  2. I changed four small units in the last layer. Two of them turn on when the model is missing a real attack. The other two turn on when the model is raising a false alarm on a normal message.
  3. I connected that slot to the final answer, so these four units can push the answer towards INJECTION or towards SAFE.
  4. I made the model slightly less eager to say INJECTION, to bring the false alarms down.

In total I changed 15,363 numbers out of 184 million. That is about 0.008% of the model.

Note: I calculated every number using averages and simple statistics from example messages. I added the units one by one, and each new unit was made to fix the mistakes which were still left.

Results

I made six versions. Each new version was made because the previous one had a problem.

Version 1 and 2: looked great, but failed on new data

I built the first version using five datasets and tested it on the half I kept aside.

In the above table, version 2 catches more attacks but it also raises more false alarms. It started marking normal questions like "What's the best book on gravitation?" as attacks.

The third row is the important one. Every detection model has a cut-off score. If I simply lower the cut-off of the original model, it catches more attacks than my version 2 with the same number of false alarms. So my change was worse than changing one setting.

The reason is simple. My units learned how attacks look in my five datasets, and not how attacks look in general.

Version 3: only reducing false alarms

In this version I kept only the two units which push the answer towards SAFE. A change like this cannot create new false alarms.

On the five datasets, false alarms came down from 85 to 25. On NotInject they came down from 46.2% to 13.0%. The cost was only 6 missed attacks out of 1,907.

But on the messages written by real people there was almost no change. It had 13 fewer false alarms and caught 60 fewer attacks.

So version 3 is useful only if false alarms on scary words are your main problem.

Version 4 and 5: using more types of data

This time I used 13 different data sources to build the change. I added the Reddit jailbreaks, the attack emails, normal emails and real user messages.

I also kept 7 data sources completely aside. The model change never saw them. I did this because I stopped trusting results on data I had already looked at many times.

Is there a better signal somewhere else in the model?

After version 5 I thought this method had reached its limit. But all my changes were reading only one place in the model. So I checked the other places also.

I did a stricter test this time. I split the 13 sources into four groups. I used three groups to find a signal and tested it on the fourth group, which it had never seen. Then I counted how many of the 3,629 attacks get caught without raising more false alarms than the original model.

So I was partly wrong about the limit. There is a better signal at layer 10. In simple words, the signal is: "does any one word in the message look very strongly like an attack?"

The problem is that this signal is spread across hundreds of features. The full version cannot be built into the model easily. The version I can build gives only about one third of the improvement.

Version 6: building it anyway

I built the simple version to see what happens. I changed one part of layer 11 so that it finds the word which looks most like an attack, and passes that value to the last layer.

The part works correctly. The value which reaches the last layer matches what I wanted, and adding it changed only 10 answers out of 38,648.

But it did not help detection. It caught only about 28 more attacks, and it made no improvement on top of version 5. It also changes 234,357 numbers instead of 15,363.

So version 5 is still the best one.

Does this beat normal training?

This is the question I had left open. Normal training means backpropagation: show the model examples and let it adjust its own weights step by step. So I ran it on the same data and compared it with version 5.

I trained three models. All three saw only the same examples from the 13 sources which I used to build version 5. I ran each one three times with a different random seed.

  • Same weights: training is allowed to change only the same numbers which version 5 changed, and nothing else.
  • Last layer: training is allowed to change the whole last part of the model where my change lives. That is 5.3 million numbers.
  • Full fine-tuning: training is allowed to change all 184 million numbers. I used one standard setting and did not tune it.

To keep the comparison fair, I set the cut-off score of every model so that it raises the same number of false alarms as version 5. Then I counted the attacks caught.

"3,276 to 3,301" is the lowest and highest result of the three runs. The same weights row has 15,365 numbers because version 5 also moved the two final bias numbers.

So the answer is no. My hand change does not beat normal training.

Full fine-tuning is better on both sets. On the 7 sources it never saw, it catches around 400 to 500 more attacks than version 5 with the same 78 false alarms. With the normal cut-off it also raises fewer false alarms on the first set, 112 to 127 against 202 for version 5.

The same weights row is the closest comparison, because it has the same budget as my change. On new examples from the 13 sources, training won in all three runs. On the 7 sources never seen it is a tie. Two runs were better than version 5 and one run was worse.

There is one place where the hand change did better. Training only the last layer was worse than version 5 on the 7 sources never seen, in all three runs. It learned my 13 sources well but it carried less of that to new sources.

Two more things I noticed about full fine-tuning. Most of its improvement on the 7 sources came from LLMail-Inject phase 2, where it went from 715 attacks caught to around 1,300. Those emails are close to the phase 1 emails it trained on. And in one run it lost some attacks in other languages, going from 956 caught to 917.

Observations and Analysis

Looking inside the model before changing it was very useful. I found that the last part of the last layer throws away something the model already knows, and that told me exactly where to make the change.

Changing a few thousand numbers by hand can give a big improvement on the type of data you used to build the change. It gives only a small improvement on new types of data.

Normal fine-tuning on the same data beats the hand change. Even when training is allowed to touch only the same 15,363 numbers, it does as well or better. So I see this method as a way to understand a model, and not as a replacement for training.

Note: Always compare your changed model with the original model at the same number of false alarms. Two times I had a better looking score but actually a worse model.

Note: Always keep some data sources completely aside, and read the actual messages in your datasets. I removed one dataset because the original model marked 82% of its normal messages as attacks. When I read the messages, I could not tell its normal messages and attack messages apart myself. The labels were the problem and not the model.

Things to keep in mind

  • The improvement on the 7 unseen sources is small. I tried five settings in the last step and only one of them improved both numbers. I picked it after looking at those results.
  • In the stricter test, where one full group of sources is hidden, the four units did not beat the original model on both numbers. The change works much better on new examples from known sources than on totally new sources.
  • I looked at the first test sets many times while building versions 1 to 3. So those numbers are not a clean test anymore.
  • Some datasets have wrong labels. For example, deepset marks simple role play requests as attacks.
  • The model reads only the first 512 pieces of a message. If an attack is hidden late in a long email, no version can see it.
  • In the comparison with normal training, I did not tune the full fine-tuning settings and I ran only three seeds. A tuned run could do even better.
  • For the 7 sources never seen, the cut-off in that comparison was set on those same messages, in the same way for every model. Also, the same weights and last layer models were scored by an exact calculation of the last layer and were not saved as models.

How to run it yourself

pip install modal && modal setup
modal run wsp_app.py --stage prep        # download model and five datasets
modal run wsp_app.py --stage baseline    # baseline model scores
modal run wsp_app.py --stage diagnose    # check each layer
modal run wsp_app.py --stage oracle      # find where the signal is lost
modal run wsp_eval2.py --version v3      # test on messages written by real people
modal run wsp_v4.py --stage prep         # 13 sources to build, 7 kept aside
modal run wsp_v4.py --stage select       # the stricter test
modal run wsp_v4.py --stage final --cfg '{"lam":0.3,"fn_q":0.99,"fp_q":0.995,"fn_delta":16,"fp_delta":16,"rounds":2,"order":["fn","fp"]}'
modal run wsp_v4.py --stage bake --cfg 3.79   # version 5
modal run wsp_probe.py --stage combo     # search for a better signal
modal run wsp_v6.py                      # version 6
modal run wsp_backprop.py                # compare with normal training

The code which changes the weights is in wsp_path.py. It is about 120 lines. The numbers behind every table are in the results folder. The changed model (version 5) is on Hugging Face: rootxhacker/deberta-v3-base-prompt-injection-v2-weight-edited.
