I tried to fix a prompt-injection detector by editing its weights by hand

No fine-tuning, no gradients. Just reading the network, working out what's broken, and writing a few thousand numbers into it. It sort of worked. Here's the whole story, including the parts where I fooled myself.

November 2026 · code and results on GitHub · built with Claude Code, run on Modal

A while back I read Rikiya Takehi's post on weight-space programming. The pitch is that a network's weights are a program, and you can read and edit that program directly instead of leaving everything to an optimizer. In one of his experiments a small Qwen model stops looping after a single direction is removed from two layers.

I wanted to know if the same idea works on something I actually care about, which is a prompt-injection classifier. These models have a well-known annoying habit. Say "please ignore the typo above" and they scream INJECTION. So the goal was easy to state: fewer false alarms, more real attacks caught, and no training.

The short version is that I got a big improvement on the kind of data I designed the edit on, and a small one on data it had never seen. Along the way I built two versions that looked great and were, on closer inspection, worse than just moving the threshold.

The model and the rules

The target is protectai/deberta-v3-base-prompt-injection-v2, a 184M-parameter DeBERTa that outputs SAFE or INJECTION. I kept its default 0.5 threshold everywhere.

The rules I set for myself were simple. Forward passes are fine for poking around, but every weight I change has to come from something closed-form, like a mean, a covariance or a quantile. No gradient steps anywhere.

Two terms I'll use a lot. TPR is the share of attacks the model catches. FPR is the share of harmless prompts it wrongly flags.

What's actually going wrong inside

Before changing anything I wanted to know whether the model is genuinely confused by these prompts, or whether it knows better and just doesn't say so. So at every layer I took the CLS token and asked whether one direction can tell a wrongly flagged harmless prompt apart from a real attack.

So it knows. Around layers 7 and 8 the two groups are almost perfectly separable, and then the distinction fades before the classifier gets to use it. I narrowed it down further, and the culprit turned out to be the very last feed-forward block. Reading the CLS state right before that block gave me about 15% false positives on the scary-word prompts. Reading right after it gave 30%.

This was the fun part of the project. It's a specific, checkable claim about one block of one layer, and it tells you exactly where to operate.

The edit

There's a nice property to exploit here. The classifier only ever looks at the CLS token of the last layer, so I can rewire the last layer however I like and no other token will notice.

Free up a wireI pick one coordinate of the residual stream (number 66) and clear it out, so nothing else writes there.
Add four detectorsFour feed-forward units read the CLS state from before the damage. Two fire on attacks the model is missing, two on harmless text it's flagging.
Read the wireTwo pooler units read that coordinate into the final logit. Since gelu(z) − gelu(−z) = z, a plus/minus pair gives an exactly linear readout.
Nudge the biasI shift the classifier bias toward SAFE, trading some of the gain for fewer false alarms.

Each detector is gelu(s·(v·h − t)). The direction v separates the examples it should fire on from the ones it should leave alone. The threshold t sits at a high quantile of that second group, so the unit stays quiet for them. I add units one at a time, each aimed at whatever errors are left.

All told that's 15,363 weights out of 184 million, about 0.008%. With no detector firing, the rewiring moves any logit by at most 0.07, so the model is otherwise untouched.

Ouch. My clever edit lost to turning one knob. It was now flagging things like "What's the best book on gravitation?" The detectors I'd built for missed attacks had learned what attacks look like in my five datasets, and not much else.

v1 had an extra problem on top of that. It flagged 8.9% of harmless "act as a…" prompts, up from 1.1%. v2 fixed that one, at least.

v3: only the false-alarm detectors

Next I kept just the two units that push toward SAFE. An edit like that can't create new false alarms, which felt like a safer bet. On the original five datasets, false positives dropped from 85 to 25 and the scary-word rate went from 46.2% to 13.0%, for the price of six missed attacks out of 1,907.

On the human-written set it was a wash: 13 fewer false alarms, 60 fewer attacks caught. Useful if scary-word false alarms are your one problem. Not what I was after.

v4 and v5: a wider diet

The obvious fix was to design on more varied data. I grew the pool to 13 sources, adding the Reddit jailbreaks, the attack emails, real benign emails and real user prompts. I also set aside seven sources that the edit would never get to see, because by now I didn't trust any number that came from data I'd been staring at.

Was I just reading the wrong place?

At this point I'd concluded the approach was near its limit. I got pushed on that, and fairly. Every edit so far had read one spot, the CLS token going into the last block. Maybe a better signal was sitting somewhere else.

So I ran a stricter test. Split the 13 sources into four groups, fit a readout on three, score it on the fourth. The question is how many of the 3,629 attacks you catch while making no more false alarms than the original model.

So I was wrong about the limit, at least partly. There is a signal that carries over to new sources, and it has an intuitive shape: does any single token light up strongly for some feature. The catch is that it's smeared across hundreds of features and needs a true max over tokens. Average instead of max and it disappears.

One more thing fell out of this that I wish I'd known earlier. Plain difference-of-means directions carried over to new sources far better than the whitened ones I'd been using in my detectors.

v6: building the one-head version anyway

The version a single attention head can compute was only worth about a third of the full signal, but I built it to see. One head in layer 11 now attends to whichever token projects most strongly onto my direction, writes that value onto a second cleared coordinate, and a reader in the last layer picks it up.

Mechanically it's lovely. The value that arrives correlates 0.85 with the true max, and installing the whole thing flips 10 predictions out of 38,648. And it does almost nothing for detection. It's worth about 28 extra attacks by itself, and it's slightly negative on top of the four detectors. It also touches 234,357 weights instead of 15,000. v5 stays the one I'd use.

What I'd be careful about

The improvement on never-seen sources is thin. I tried five bias settings, and the one I'm reporting was the only one that improved both numbers there. I picked it with those results in front of me. Treat it as "probably slightly better", not as a headline.

The strict group-out test was more pessimistic than the final numbers. When a whole source is hidden during design, no setting of the four-detector edit beat the original model on both counts. The edit handles new examples from familiar places much better than it handles new places.

Ranking quality on the never-seen sources dipped a little (AUROC 97.3 to 96.8). The gain is at the 0.5 threshold, not everywhere.

I looked at the five-dataset test split and the first human-written set many times while iterating. They're development data at this point, whatever I called them at the start.

Some labels are shaky. deepset marks plain role-play requests as attacks. The "regular" Reddit prompts include obvious jailbreaks. And I threw out one synthetic dataset entirely after reading it. The original model flagged 82% of its "benign" rows, which looked insane until I saw that its benign and attack rows were basically indistinguishable.

Inputs are cut at 512 tokens, so an attack buried late in a long email is invisible to every version here.

And the big one. I never ran ordinary fine-tuning on the same data. That's the comparison that would tell you whether any of this is worth the trouble.

What I took away

Reading the network first was worth it. "The last block throws away a distinction the model already made" is a concrete finding, and it pointed straight at the fix.

A handful of hand-written units can move the numbers a lot on the data you built them from. That tells you very little about anywhere else.

Compare against the original model at the same false-positive count, every time. Twice I had a better headline number and a worse model.

Hold out whole sources, and read the rows. The 82% dataset would have wrecked my conclusions if I'd only looked at the table.

Run it yourself

pip install modal && modal setup
modal run wsp_app.py --stage prep        # model + five datasets
modal run wsp_app.py --stage baseline
modal run wsp_app.py --stage diagnose    # per-layer probes
modal run wsp_app.py --stage oracle      # where the signal is lost
modal run wsp_eval2.py --version v3      # human-written eval set
modal run wsp_v4.py --stage prep         # 13 design sources + 7 never-seen
modal run wsp_v4.py --stage select       # group-out test
modal run wsp_v4.py --stage final --cfg '{"lam":0.3,"fn_q":0.99,"fp_q":0.995,"fn_delta":16,"fp_delta":16,"rounds":2,"order":["fn","fp"]}'
modal run wsp_v4.py --stage bake --cfg 3.79   # v5
modal run wsp_probe.py --stage combo     # the search for a signal that carries over
modal run wsp_v6.py                      # the attention-head circuit

The edit lives in wsp_path.py and is about 120 lines. The numbers behind every table are in the results/ folder. I haven't uploaded the edited weights, but the commands above rebuild them.
